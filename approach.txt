================================================================================
  1. THE CONCEPT — WHAT IS GHOSTPROCESS?
================================================================================

GhostProcess is a 4-seat AI dark factory that treats software development
like a courtroom trial:

  - The ARCHITECT plans the case (decomposes the task)
  - The CODER builds the defense (implements the code)
  - The GHOST AUDITOR prosecutes (tries to BREAK the code with adversarial tests)
  - The GATEKEEPER judges (accepts only what survives adversarial attack)

The key insight: most factories have agents that check if code WORKS.
GhostProcess has an agent whose entire job is to prove the code FAILS.
Only code that survives active attack ships.

This is a RED TEAM approach to software factories.

Why "Ghost"? The auditor operates in the dark — it never sees the Coder's
tests. It derives its attacks purely from the spec. If the Coder's code
can survive attacks from an agent that has zero knowledge of the
implementation, that code is genuinely robust.

================================================================================
  2. TRACK CHOICE — POCKETFUL (PAYMENTS/WALLET)
================================================================================

Track: Pocketful (Venmo-like wallet & payments app)

WHY THIS TRACK:
- The core invariant is simple and absolute: "money must never be created,
  destroyed, or spent twice"
- This is PERFECT for adversarial testing — double-spend, race conditions,
  rounding errors are all attack vectors
- Double-entry bookkeeping is a well-known pattern that LLM agents can
  implement confidently
- Judges from PayPal, Meta, Amazon — they know payments systems

THE HARD PARTS (from the spec):
- Money must never be created, destroyed, or spent twice
- Must handle concurrent transfers correctly
- Must handle retries without duplicating transactions
- Must handle rounding correctly (no penny creation/destruction)

4.2 KEY DESIGN PATTERNS
------------------------

  DOUBLE-ENTRY LEDGER:
    Every transfer creates exactly 2 journal entries:
      - DEBIT:  source wallet  -amount
      - CREDIT: dest wallet    +amount
    
    Invariant: SUM(all journal entries) == 0 ALWAYS
    This is the fundamental correctness guarantee.

    Table: journal_entries
    +----+----------------+----------------+--------+------------+----------+
    | id | transaction_id | wallet_id      | amount | created_at | entry_type|
    +----+----------------+----------------+--------+------------+----------+
    | 1  | txn_abc123     | wallet_alice   | -50.00 | ...        | DEBIT    |
    | 2  | txn_abc123     | wallet_bob     | +50.00 | ...        | CREDIT   |
    +----+----------------+----------------+--------+------------+----------+

    Wallet balance = SUM(journal_entries WHERE wallet_id = X)

  IDEMPOTENCY:
    Every write request includes an idempotency_key (client-generated UUID)
    
    Table: idempotency_keys
    +------------------+--------+-----------+
    | idempotency_key  | status | response  |
    +------------------+--------+-----------+
    | req_xyz789       | DONE   | {json...} |
    +------------------+--------+-----------+

    On duplicate key: return cached response, don't re-execute
    This makes retries safe — same request = same result

  ATOMIC TRANSFERS:
    All balance changes wrapped in database transactions
    Use SQLite's built-in transaction isolation
    No partial transfers possible — either both entries write or neither does

  STATE IMPORT/EXPORT:
    POST /state/import — load a complete state snapshot (for test harness)
    GET  /state/export — dump complete state (wallets + journal + balances)
    Used by the grading harness to set up test scenarios


4.3 API DESIGN (Stage 1)
-------------------------

  Wallets:
    POST   /wallets                 Create a new wallet
    GET    /wallets/{id}            Get wallet details + balance
    GET    /wallets                 List all wallets

  Transfers:
    POST   /transfers               Transfer money between wallets
      Body: {
        "idempotency_key": "uuid",
        "source_wallet_id": "string",
        "destination_wallet_id": "string",
        "amount": "string (decimal)"    <-- string to avoid floating point
      }
    GET    /transfers/{id}          Get transfer details
    GET    /transfers               List transfers (with filters)

  State (for harness):
    POST   /state/import            Import full state snapshot
    GET    /state/export            Export full state snapshot
    POST   /state/reset             Reset to clean state

  Health:
    GET    /health                  Health check


4.4 DATA MODEL
--------------

  wallets:
    id              TEXT PRIMARY KEY (UUID)
    name            TEXT
    created_at      DATETIME
    updated_at      DATETIME

  journal_entries:
    id              INTEGER PRIMARY KEY AUTOINCREMENT
    transaction_id  TEXT NOT NULL (links debit + credit)
    wallet_id       TEXT NOT NULL (FK -> wallets.id)
    amount          TEXT NOT NULL (decimal as string, no float!)
    entry_type      TEXT NOT NULL (DEBIT or CREDIT)
    created_at      DATETIME NOT NULL

  idempotency_keys:
    key             TEXT PRIMARY KEY
    status          TEXT NOT NULL (PENDING, DONE, FAILED)
    response_body   TEXT (cached JSON response)
    created_at      DATETIME NOT NULL

  transfers:
    id              TEXT PRIMARY KEY (UUID)
    idempotency_key TEXT UNIQUE
    source_wallet   TEXT NOT NULL (FK -> wallets.id)
    dest_wallet     TEXT NOT NULL (FK -> wallets.id)
    amount          TEXT NOT NULL
    status          TEXT NOT NULL (PENDING, COMPLETED, FAILED)
    created_at      DATETIME NOT NULL

  CRITICAL: All monetary amounts stored as TEXT (decimal strings).
  Use Python's `decimal.Decimal` for all arithmetic.
  NEVER use float for money. Ever.

5.3 SEAT 3: GHOST AUDITOR — "The Breaker" ★ KEY DIFFERENTIATOR ★
------------------------------------------------------------------
  Runtime:        BAND Python SDK + Google Gemini 2.5 Flash / Groq Llama 3.3 70B (100% FREE)
  Role:           Adversarial testing — tries to BREAK the code

  What it does:
    1. Reads ONLY the Architect's design document (NOT the Coder's tests)
    2. Derives attack vectors from the spec and invariants
    3. Writes adversarial test scenarios that try to:
       - Violate invariants (e.g., create money from nothing)
       - Exploit race conditions (concurrent conflicting operations)
       - Break idempotency (duplicate requests producing different results)
       - Trigger rounding errors (penny creation/destruction)
       - Crash the system (malformed input, boundary values)
       - Exploit state inconsistencies (partial failures)
    4. Runs each attack against the Coder's implementation
    5. Reports results: SURVIVED or BREACHED for each attack
    6. If any attack succeeds (code breaks): sends BREACH REPORT to room
    7. If all attacks fail (code holds): sends CLEARANCE REPORT to room

  Handoff Output:
    - AUDIT_REPORT.md with:
      - List of every attack attempted
      - Attack methodology
      - Result (SURVIVED / BREACHED)
      - Reproduction steps for any breach
    - adversarial_tests/ directory with all test scripts

  MANDATE (Generic — this is the crown jewel):
  """
  You are the Ghost Auditor. You are an adversarial testing agent. Your
  sole purpose is to find bugs, vulnerabilities, and invariant violations
  in code written by another agent.

  CRITICAL RULES:
  1. You must NEVER read the other agent's test suite. You derive your
     tests independently from the design specification.
  2. You are not here to confirm the code works. You are here to prove
     it DOESN'T. Approach every system as if it has hidden bugs.
  3. You must try to break every invariant listed in the design.

  Attack categories you must attempt:
  A. INVARIANT VIOLATION: Can you make a property that "must always hold"
     become false? Try boundary values, negative numbers, zero, maximum
     values, and forbidden states.
  B. CONCURRENCY ATTACK: Can you cause a race condition? Send simultaneous
     conflicting requests. Try double-spending, double-booking, or
     simultaneous reads and writes.
  C. IDEMPOTENCY VIOLATION: Does sending the same request twice produce
     different results? Try rapid retries, delayed retries, and retries
     after partial failure.
  D. PRECISION ATTACK: Can you create or destroy fractional units through
     rounding? Try splitting and recombining values, very small amounts,
     and very large amounts.
  E. STATE CORRUPTION: Can you leave the system in an inconsistent state?
     Try operations that fail halfway, import invalid state, and query
     during writes.
  F. INPUT FUZZING: Does the system handle malformed, missing, or extreme
     input gracefully? Try empty strings, null values, negative numbers,
     strings where numbers are expected, and very long inputs.

  Output format:
  - Write each attack as a runnable test script
  - Save all attacks to an adversarial_tests/ directory
  - Create AUDIT_REPORT.md with:
    * Attack ID, category, description
    * Expected behavior vs actual behavior
    * Verdict: SURVIVED or BREACHED
    * Reproduction steps for any BREACHED attack
  - Post the verdict to the room:
    * If ANY attack breaches: "BREACH — [count] vulnerabilities found"
    * If ALL attacks survived: "CLEARANCE — all attacks survived"
  """


5.4 SEAT 4: GATEKEEPER — "The Judge"
--------------------------------------

    5. If ACCEPTED: posts final RELEASE.md and marks work as done
    6. The Coder fixes and re-triggers Auditor review (loop until ACCEPT)

    * The implementation agent reports all tests passing
    * The adversarial agent reports all attacks survived

    * Any test failure is reported
    * Any adversarial attack succeeded (breached)

  On ACCEPT:

  12. RISK MITIGATION
================================================================================

  RISK: BAND Desktop doesn't work properly on Windows
  MITIGATION: Join BAND Discord early. Have Linux VM ready as backup.
  Many participants reported issues (see "bandisworstforme" submission).

  RISK: Gemini Free Tier rate limits (15 RPM)
  MITIGATION: The free tier provides 15 RPM and 1,500 requests/day at $0.00.
  Add request pacing (3-4 second sleep between LLM calls) in `gemini_client.py`.
  If rate limits are ever approached, the client automatically falls back to
  Groq Cloud's free tier (Llama 3.3 70B), ensuring zero downtime and 100% free operation.

  RISK: Agents don't collaborate well / get confused
  MITIGATION: Do a dry run with a simple task first. Refine mandates
  based on what breaks. Keep mandates short and specific.

  RISK: Not enough time for Stage 2
  MITIGATION: Stage 1 alone is enough to be eligible. Focus on making
  Stage 1 + the factory design excellent rather than rushing Stage 2.

  RISK: Adversarial tests are too aggressive / break the pipeline
  MITIGATION: Ghost Auditor mandate includes clear output format.
  Gatekeeper has clear decision rules. The loop is bounded.

  13. WHAT MAKES GHOSTPROCESS UNIQUE
================================================================================

  Looking at ALL current submissions on lablab.ai:

  - "Fail Closed": Auditor can't edit code (tool denial). GhostProcess
    goes further — auditor actively GENERATES attacks.

  - "Four Seats Factory": Focuses on evidence reproduction. GhostProcess
    focuses on evidence GENERATION through adversarial testing.

  - "Obsidian Foundry": Tester writes tests from spec. GhostProcess's
    Ghost Auditor writes ATTACKS from spec — adversarial, not just tests.

  - "Pocketful Dark Factory": Standard 3-agent pipeline. GhostProcess
    adds the adversarial 4th agent as a differentiator.

  UNIQUE SELLING POINTS:
  1. Red-team agent that generates attacks, not just runs tests
  2. Courtroom metaphor (defense vs prosecution vs judge)
  3. Ghost Auditor is blind to implementation tests — independent verification
  4. Explicit feedback loop: reject -> fix -> re-audit -> accept
  5. The factory ITSELF is designed to catch the hardest bugs in payments
