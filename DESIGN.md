# Technical Architecture Design

## 1. System Overview & Component Topology
```
┌─────────────────────────────────────────────────────────────────────┐
│                         FastAPI Application                         │
│                                                                     │
│  ┌───────────────┐   ┌─────────────────────┐   ┌─────────────────┐ │
│  │   Transport   │   │   Business Services │   │   Persistence   │ │
│  │   (Uvicorn)   │   │   (Async Python)    │   │   (SQLAlchemy) │ │
│  └───────┬───────┘   └───────┬─────┬───────┘   └───────┬─────┬───┘ │
│          │                 │     │                 │     │     │
│   ┌──────▼───────┐   ┌─────▼─────▼─────┐   ┌───────▼─────▼─────┐ │
│   │   Routers    │   │   Service Layer │   │   DB Models &    │ │
│   │ (health,    │   │ (wallet, transfer│   │   Schema         │ │
│   │  wallets,   │   │  state)          │   │ (SQLite WAL)     │ │
│   │  transfers,│   └─────────────────┘   └───────────────────┘ │
│   │  state)     │                                             │
│   └─────────────┘                                             │
└─────────────────────────────────────────────────────────────────┘
```

* **Transport Layer** – `uvicorn` runs the ASGI app, exposing HTTP endpoints.
* **Router Layer** – FastAPI routers (`health.py`, `wallets.py`, `transfers.py`, `state.py`) perform request validation and delegate to services.
* **Service Layer** – Pure‑Python async services contain all business rules, invariant enforcement, and transaction orchestration.
* **Persistence Layer** – Async SQLAlchemy 2.0 models mapped to SQLite tables. All writes occur inside a **single `BEGIN IMMEDIATE` transaction** to guarantee a write‑lock before any read.

All components are **strictly decoupled**: routers have no direct DB access, services have no HTTP knowledge, and models are pure data structures.

## 2. Mathematical Invariants & Conservation Guarantees

| # | Invariant Description | Formal Expression | Enforcement Point |
|---|-----------------------|-------------------|--------------------|
| I1 | **Double‑Entry Ledger** – Every monetary transfer creates exactly two journal entries: one DEBIT (negative) on the source wallet and one CREDIT (positive) on the destination wallet. | `|JE_transfer| = 2 ∧ JE_source.amount = -A ∧ JE_dest.amount = +A` | `transfer_service.create_transfer()` – inserts both entries in the same transaction. |
| I2 | **Zero‑Sum Ledger** – The sum of *all* journal entry amounts across the entire system is always zero. | `Σ_{e∈JournalEntries} e.amount = 0` | Database constraint enforced by **post‑commit verification** (assertion) and by the import endpoint (rejects non‑zero sum). |
| I3 | **Derived Balance** – A wallet’s balance is never stored; it is computed as the sum of its journal entries. | `balance(w) = Σ_{e∈JournalEntries, e.wallet_id = w.id} e.amount` | `wallet_service.get_balance()` computes on‑fly; `wallet_service.list_wallets()` includes computed balance. |
| I4 | **Non‑Negative Balance** – No wallet may ever have a negative derived balance. | `balance(w) ≥ 0 ∀ w` | Checked **inside the same `BEGIN IMMEDIATE` transaction** before journal entries are persisted. |
| I5 | **Exact Decimal Arithmetic** – All monetary values are `Decimal` with **exact two‑decimal‑place quantization**. No binary floating point is ever used. | `amount ∈ Decimal ∧ amount.quantize(0.01) == amount` | Pydantic validators (`DecimalValidator`) reject >2 decimal places; service layer normalizes <2 places. |
| I6 | **Idempotent Mutations** – Re‑submitting a request with the same `idempotency_key` yields the *identical* HTTP status and response body without re‑executing state changes. | `response(key) = response(key)` | `idempotency_records` table stores `status_code` and serialized `response_body`. Service checks this table before any mutation. |
| I7 | **Atomicity** – Debit and credit journal entries, the transfer record, and the idempotency record are committed atomically. | `COMMIT ⇔ all four rows persisted` | Single `session.begin()` block with `BEGIN IMMEDIATE`. |

All invariants are **mathematically provable** from the immutable ledger (`journal_entries`) and are never violated by any code path.

## 3. Data Persistence Schema & Integrity Constraints

All tables are created with **SQLite PRAGMA** settings at application start:

```sql
PRAGMA journal_mode = WAL;
PRAGMA busy_timeout = 5000;   -- milliseconds
PRAGMA foreign_keys = ON;
```

### 3.1 `wallets`
| Column      | Type   | Constraints                         | Description |
|-------------|--------|-------------------------------------|-------------|
| `id`        | TEXT   | PRIMARY KEY                         | UUID v4 generated by service |
| `name`      | TEXT   | NULLABLE                            | Human‑readable label |
| `created_at`| TEXT   | NOT NULL                            | ISO‑8601 UTC timestamp |
| `updated_at`| TEXT   | NOT NULL                            | ISO‑8601 UTC timestamp |

*No balance column – balance is derived.*

### 3.2 `transfers`
| Column               | Type   | Constraints                                 | Description |
|----------------------|--------|---------------------------------------------|-------------|
| `id`                 | TEXT   | PRIMARY KEY                                 | UUID v4 |
| `idempotency_key`   | TEXT   | UNIQUE NOT NULL                             | Client supplied |
| `source_wallet_id`   | TEXT   | NOT NULL, FK → wallets(id)                  | Debit side |
| `dest_wallet_id`     | TEXT   | NOT NULL, FK → wallets(id)                  | Credit side |
| `amount`             | TEXT   | NOT NULL                                    | Positive decimal string (`"12.34"`). Stored as TEXT to avoid floating point. |
| `status`             | TEXT   | NOT NULL CHECK(status IN ('COMPLETED','FAILED')) | Transfer outcome |
| `created_at`         | TEXT   | NOT NULL                                    | ISO‑8601 UTC |

### 3.3 `journal_entries`
| Column          | Type      | Constraints                                 | Description |
|-----------------|-----------|---------------------------------------------|-------------|
| `id`            | INTEGER   | PRIMARY KEY AUTOINCREMENT                   | Monotonic sequence |
| `transaction_id`| TEXT      | NOT NULL, FK → transfers(id)                | Links to the transfer that generated the entry |
| `wallet_id`     | TEXT      | NOT NULL, FK → wallets(id)                  | Wallet affected |
| `amount`        | TEXT      | NOT NULL                                    | Signed decimal string (`"-12.34"` or `"12.34"`). |
| `entry_type`    | TEXT      | NOT NULL CHECK(entry_type IN ('DEBIT','CREDIT')) | Semantic type |
| `created_at`    | TEXT      | NOT NULL                                    | ISO‑8601 UTC |

### 3.4 `idempotency_records`
| Column        | Type   | Constraints               | Description |
|---------------|--------|---------------------------|-------------|
| `key`         | TEXT   | PRIMARY KEY               | Client‑provided idempotency key |
| `status_code` | INTEGER| NOT NULL                  | HTTP status returned on first execution |
| `response_body`| TEXT  | NOT NULL                  | JSON‑encoded response payload |
| `created_at`  | TEXT   | NOT NULL                  | ISO‑8601 UTC |

### 3.5 Indexes
* `idx_journal_wallet` on (`wallet_id`) – fast balance aggregation.
* `idx_transfer_source_dest` on (`source_wallet_id`, `dest_wallet_id`) – lookup for wallet‑scoped transfer queries.

## 4. REST Interface Contracts

All request/response bodies use **JSON** with **string‑encoded decimals**. Errors follow FastAPI’s standard `{"detail": "..."}` schema.

### 4.1 Health
| Method | Path | Request | Success Response | Errors |
|--------|------|---------|------------------|--------|
| `GET` | `/health` | – | `200 OK` <br>`{ "status":"healthy", "service":"ghostprocess-pocketful", "timestamp":"<ISO8601>" }` | – |

### 4.2 Wallets

| Method | Path | Request Body | Success Response | Errors |
|--------|------|--------------|------------------|--------|
| `POST` | `/wallets` | `{ "name": "Alice", "idempotency_key": "<UUID>" }` | `201 Created` <br>`{ "id":"<uuid>", "name":"Alice", "balance":"0.00", "created_at":"<ISO>" }` | `400` – duplicate idempotency key, malformed payload |
| `GET` | `/wallets/{wallet_id}` | – | `200 OK` <br>`{ "id":"<uuid>", "name":"Alice", "balance":"<Decimal>", "created_at":"<ISO>" }` | `404` – wallet not found |
| `GET` | `/wallets` | – | `200 OK` <br>`[ {wallet objects…} ]` | – |

*Balance is computed on‑demand via `wallet_service.get_balance()`.*

### 4.3 Transfers

| Method | Path | Request Body | Success Response | Errors |
|--------|------|--------------|------------------|--------|
| `POST` | `/transfers` | `{ "idempotency_key":"<UUID>", "source_wallet_id":"<uuid>", "destination_wallet_id":"<uuid>", "amount":"<Decimal>" }` | `201 Created` (first execution) **or** `200 OK` (idempotent replay) <br>`{ "id":"<uuid>", "idempotency_key":"<UUID>", "source_wallet_id":"...", "destination_wallet_id":"...", "amount":"...", "status":"COMPLETED", "created_at":"<ISO>" }` | `400` – invalid amount, >2 decimals, zero/negative amount, insufficient funds, self‑transfer <br>`404` – source or destination wallet missing |
| `GET` | `/transfers/{transfer_id}` | – | `200 OK` <br>`{ transfer object }` | `404` – not found |
| `GET` | `/transfers` | Query params: `wallet_id` (optional), `limit` (default 50), `offset` (default 0) | `200 OK` <br>`[ transfer objects … ]` | – |

**Validation Rules (enforced by Pydantic + service layer):**
* `amount` must match regex `^\d+(\.\d{1,2})?$` and be > 0.00.
* If `amount` has 1 decimal place, it is **normalized** to two places (`"10.1"` → `"10.10"`).
* More than two decimal places cause a `400` rejection.

### 4.4 State Management (Test Harness)

| Method | Path | Request Body | Success Response | Errors |
|--------|------|--------------|------------------|--------|
| `POST` | `/state/reset` | – | `200 OK` <br>`{ "status":"reset_successful" }` | – |
| `POST` | `/state/import` | `{ "wallets":[{ "id":"...", "name":"...", "balance":"<Decimal>" }], "journal_entries":[{ "transaction_id":"...", "wallet_id":"...", "amount":"<Decimal>", "entry_type":"DEBIT|CREDIT" }] }` | `200 OK` <br>`{ "imported_wallets":N, "imported_entries":M }` **or** `400 Bad Request` if imported ledger sum ≠ 0.00 | – |
| `GET`  | `/state/export` | – | `200 OK` <br>`{ "wallets":[…], "transfers":[…], "journal_entries":[…], "ledger_sum":"0.00" }` | – |

*Import* runs inside a single transaction; if the zero‑sum check fails, the whole import is rolled back.

## 5. Transaction Isolation, Locking, & Idempotency Engine

### 5.1 Write‑Lock‑Before‑Read Pattern
Every mutating endpoint (`POST /wallets`, `POST /transfers`, `POST /state/import`) follows:

```python
async with async_session() as session:
    async with session.begin():
        await session.execute(text("BEGIN IMMEDIATE"))   # Acquire exclusive write lock
        # 1️⃣ Idempotency lookup (idempotency_records)
        # 2️⃣ Domain validation (balances, existence, decimal precision)
        # 3️⃣ Insert primary record (wallet or transfer)
        # 4️⃣ Insert exactly two journal entries (DEBIT/CREDIT)
        # 5️⃣ Insert idempotency cache entry with status & response payload
        # 6️⃣ Commit (implicit on exit of `session.begin()`)
```

*The lock is held for the entire transaction, guaranteeing that no concurrent transaction can read a stale balance and cause a double‑spend.*

### 5.2 Idempotency Workflow
1. **Lookup** – `SELECT * FROM idempotency_records WHERE key = :key`.
2. **Cache Hit** – Return stored `status_code` and `response_body` immediately.
3. **Cache Miss** – Execute business logic inside the `BEGIN IMMEDIATE` block.
4. **Persist** – After successful commit, insert a row into `idempotency_records` with the exact response that was sent.
5. **Concurrency Safety** – The `key` column is a primary key; concurrent attempts to insert the same key raise an `IntegrityError`, which is caught and transformed into a cache‑hit response.

### 5.3 Decimal Handling (Pydantic v2)

```python
from decimal import Decimal, ROUND_DOWN, InvalidOperation

def parse_decimal(value: str) -> Decimal:
    try:
        d = Decimal(value)
    except InvalidOperation:
        raise ValueError("Invalid decimal format")
    # Reject more than 2 decimal places
    if d.as_tuple().exponent < -2:
        raise ValueError("More than two decimal places are not allowed")
    # Normalize to exactly two places (quantize)
    return d.quantize(Decimal("0.01"), rounding=ROUND_DOWN)
```

All schemas reference this validator; the service layer stores the **string representation** (`str(d)`) in the DB.

## 6. Lifecycle Management (Reset / Import / Export)

*Implemented in `routes/state.py` and `services/state_service.py`.*

| Endpoint | Action | Transaction Scope | Invariant Checks |
|----------|--------|-------------------|------------------|
| `POST /state/reset` | Truncate all tables (`DELETE FROM …`) | Single transaction | Guarantees empty ledger → sum = 0 |
| `POST /state/import` | Bulk insert wallets + journal entries | Single transaction | After insert, compute `SUM(amount)`; abort if ≠ 0.00 |
| `GET /state/export` | Read‑only dump of all tables + computed balances | Read‑only transaction (`BEGIN`) | Returns `ledger_sum` for external verification |

All three endpoints are **protected by a dedicated admin token** (environment variable `ADMIN_TOKEN`) to prevent accidental misuse in production; the token is required via `Authorization: Bearer <token>` header.

## 7. Failure Taxonomy & Status Code Mappings

| Failure Category | Trigger | HTTP Status | Response Body |
|------------------|---------|-------------|---------------|
| **Validation** | Decimal precision, missing fields, self‑transfer, negative amount | `400 Bad Request` | `{"detail":"<human readable message>"}` |
| **Resource Not Found** | Wallet or Transfer ID does not exist | `404 Not Found` | `{"detail":"<entity> not found"}` |
| **Insufficient Funds** | Balance check fails | `400 Bad Request` | `{"detail":"Insufficient funds in source wallet"}` |
| **Idempotency Conflict** | Duplicate key with different payload (should never happen) | `409 Conflict` | `{"detail":"Idempotency key conflict"}` |
| **Ledger Violation** | Zero‑sum invariant broken (import) | `400 Bad Request` | `{"detail":"Ledger sum must be zero"}` |
| **Unexpected Server Error** | Unhandled exception, DB lock timeout | `500 Internal Server Error` | `{"detail":"Internal server error"}` |

All error paths **do not mutate** any state; the transaction is rolled back automatically by SQLAlchemy’s `session.begin()` context manager.

## 8. Summary of Guarantees

* **Atomic double‑entry transfers** – never partial.
* **Zero‑sum ledger** – enforced at every commit.
* **Derived balances** – no stale stored balance.
* **Deterministic decimal arithmetic** – no floating‑point drift.
* **Idempotent API** – safe retries, exactly‑once semantics.
* **Write‑lock‑before‑read** – eliminates TOCTOU race conditions.
* **Explicit transaction isolation** – `BEGIN IMMEDIATE
